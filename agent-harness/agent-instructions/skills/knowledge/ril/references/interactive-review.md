### Brief the capture

Present a useful briefing in the first research handoff: what the item is, its original web link, what was established,
how it could help this user, the material cost or risk, and your recommended action. Research artifact paths support
that explanation; they do not replace it. Keep the opening compact and let the user's follow-up determine the depth.

For a researched batch, map each capture to its original source before focusing on the strongest recommendation. Keep
the user's selections and dispositions attached to the individual captures; a shared topic does not merge their gates.

### Explain the payoff

Explain the mechanism through one concrete use in the user's work. Name what changes from the current behavior and what
that would buy. When asked to sell an idea or figure out its value, choose a useful application and recommend the next
action instead of returning an unranked feature list or asking the user to invent the use case.

An idea that adds no useful capability can end as reference or drop. Do not manufacture a trial or framework merely to
give the capture an action. State missing evidence when it prevents choosing between a real benefit and duplication.

### Follow the selected idea

Answer the current question before repeating the batch report. Deepen the selected idea and show a concrete example when
the mechanism or proposed artifact is unclear. Preserve the other captures' individual decisions without bringing back
items the user excluded.

A conditional replacement proposal or a question about usefulness is exploration, not adoption approval. Apply the
[verdict gate](../SKILL.md#verdict-gate) to the actual requested action before installing, activating or recording it.

### Establish the approved baseline

Distinguish source claims, observed code, live behavior and the setup the user has approved. An installed component the
user does not recognize is a finding to resolve, not an accepted dependency on which to build the recommendation.
Compare against the existing owner and the user's actual replacement scope before proposing another mechanism.

### Prove a useful trial

After a trial is approved, use the requested machine, execution route and real workload. When integration is requested,
keep it removable and owned by the normal configuration. A synthetic demonstration can prove mechanics, but cannot
replace a requested real setup or prove practical benefit. Establish the removal path before testing an integration.

Measure the promised benefit against equivalent work with the same inputs and acceptance criteria. For efficiency,
separate actual token and cost evidence from byte counts and vendor savings counters. Preserve output quality in the
comparison and recommend removal when the user's rejection or the evidence rules out the proposed value.

### Route to the existing owner

When a useful capture belongs to an existing project or worker, recommend that owner and its verified intake rather than
inventing a separate implementation. Route the approved material with its source and useful takeaway; research alone
does not authorize writing to another project's files or sending a worker a message.

### Prepare bounded research

When delegation helps, write task-specific source-evidence and independent-verification briefs using the existing
[briefing guidance](../../../agent-workflows/instructions/references/subagent-briefs.md) and [workflow
budget](../../../agent-workflows/agent-harness/references/workflows.md). Bound calls for the whole batch, share
recovered evidence rather than rediscovering it, and keep synthesis and the recommendation with the lead agent.
