## What it actually is

A compact architecture sketch, not a downloadable harness, published prompt or new tool. Its useful mechanism is the
closed loop between a rule corpus and an evaluator: the writer does not merely receive style guidance once; a separate
review pass names the failed rule, sends it back to the writer and tightens the corpus from human corrections over time.

Four file groups feed the loop:

- writing rules: simplified technical English, short sentences and Zinsser's simplicity, brevity, clarity and humanity;
- `voice-dna.md`: casing, rhythm and lexicon learned from the author;
- `forbidden.md`: recurring patterns such as staccato pairs, antithesis reframes, isocolon metaphor pairs and backward
  references;
- examples: a small set of published work used as the acceptance target.

The image names model choices, but they are incidental observations from August 2026 rather than part of the pattern.

## Reasoning

Reference, not adopt. The source is a clear visual explanation of an architecture this repo already implements in a more
selective form. The one difference, an independent evaluator on every draft, is already available in `compose-page` for
high-value page work and would be wasteful as an always-on rule. Turning the diagram into another skill would create a
second home for wording policy and weaken the single-owner boundary that `humanize` establishes.

It is not a trial because there is no external implementation to exercise, and not a learn because the capture names no
new practice that needs study. It is worth filing as a reference for the feedback-loop pattern: when a recurring manual
miss is concrete enough to encode, add it to the owning `humanize` catalog and its machine or evaluation evidence rather
than accumulating a parallel personal prompt bundle.

Cost: one reference note and one source-image attachment after approval. No dependency, runtime, build or activation cost.

```markdown
## Bottom line

A writing harness can be a feedback loop rather than one large style prompt: load a bounded rule corpus, draft, have a
separate evaluator name the exact failed rules, revise, and turn recurring human corrections into new rules. The diagram
is an architecture sketch, not a downloadable tool.

## What to steal

- Keep the writer and evaluator roles distinct. The evaluator returns named defects, not a rewritten answer whose choices
  the writer cannot trace.
- Let human edits tighten the corpus only when they reveal a recurring pattern. One disliked sentence is evidence, not a
  new universal ban.
- Separate stable plain-language rules, model-era tells, channel constraints and examples so each can change for its own
  reason.
- Spend the evaluator call where the artifact earns it. A landing page or published document can justify a revision loop;
  every short chat reply cannot.
- Treat examples as an acceptance target for personal or editorial work, not as universal voice DNA for neutral technical
  surfaces.

## Fit here

The dotfiles already use this shape selectively. `humanize` owns plain language, forbidden tells and channel rules; a
Stop hook checks the mechanical subset; `compose-page` runs the expensive writer/critic/revision loop for page work. The
useful policy is to feed recurring misses back into those existing owners rather than create another writing skill.
```
